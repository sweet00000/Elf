## 1. The `.elf` container (depends on Q2 = ZIP)

### File layout

```
my_subject.elf                     ← ZIP archive, .elf extension
├── manifest.json                  ← required, machine-readable header
├── kb.json                        ← required, conforms to schema
├── runtime/
│   ├── index.html                 ← entry point (open in browser)
│   ├── runtime.js                 ← UI + wllama bootstrap
│   └── style.css
├── model/
│   └── qwen3-0.6b-q4_k_m.gguf     ← optional, ~400MB if present
└── assets/                        ← optional images/figures referenced from kb.json
    └── ...
```

### `manifest.json` schema (v1.0)

```json
{
  "elf_version": "1.0",
  "schema_version": "1.0",
  "title": "Introduction to Thermodynamics",
  "file_id": "intro_to_thermo",
  "created": "2026-05-07T12:34:56Z",
  "license": { "name": "CC BY-NC-SA 4.0" },
  "size_bytes": 423817216,
  "has_model": true,
  "model": {
    "name": "qwen3-0.6b-q4_k_m",
    "path": "model/qwen3-0.6b-q4_k_m.gguf",
    "sha256": "..."
  },
  "kb": {
    "path": "kb.json",
    "article_count": 8,
    "chunk_count": 47,
    "sha256": "..."
  },
  "tags": ["physics", "thermodynamics", "intro"],
  "discriminator_score": 0.91
}
```

`has_model: false` is a valid lite ELF — same KB and runtime, but the model
is fetched from a shared CDN URL declared in `manifest.json` instead of
bundled. This keeps catalog browsing affordable while preserving the
fully-offline option for downloads.

### Why ZIP

- Standard, inspectable, every OS unzips natively
- Browsers can read it via `JSZip` or the native Compression Streams API
  with a few lines of glue
- Random access: pull `manifest.json` + `kb.json` from a remote `.elf` over
  HTTP range requests *without downloading the model*. This is what makes
  the catalog viewable.
- ZIP central directory is at the *end* of the file → range request the
  last ~64KB to get the index, then range-request specific entries

### Loader sketch

```js
// site/runtime/loadElf.js
import { unzipSync } from 'fflate';

export async function loadElfHeader(url) {
  // Range-request just the central directory + manifest
  const head = await fetch(url, { headers: { Range: 'bytes=-65536' }})
                     .then(r => r.arrayBuffer());
  // ... parse central dir, find manifest.json offset, fetch only that
  return manifest;
}

export async function loadFullElf(url, onProgress) {
  const buf = await fetchWithProgress(url, onProgress);
  return unzipSync(new Uint8Array(buf)); // { 'manifest.json': Uint8Array, ... }
}
```

`runtime/index.html` inside the ELF is what opens when you double-click.
On open: `runtime.js` reads its own `kb.json` + boots wllama against
`model/qwen3-0.6b-q4_k_m.gguf` (if present) or the CDN fallback. Same
runtime works whether the ELF is on disk, in OPFS, or being streamed from
the catalog.

```
site/
├── index.html               ← existing landing page
├── catalog/
│   ├── index.html           ← browse + search all ELFs
│   └── catalog.json         ← static manifest, generated by build step
├── view/

│   ├── intro_to_thermo.elf
│   ├── kalman_filters.elf
│   └── ...
├── runtime/                 ← shared site runtime (separate from in-ELF runtime)
│   ├── catalog.js
│   ├── viewer.js
│   └── search.js
└── api/
    └── waitlist.js          ← edge fn for the waitlist email; later: paid-tier auth
```

Everything is static. `catalog.json` is regenerated whenever a new ELF lands
in `elfs/`. No server, no database — just a build step.

## 3. `catalog.json` — single source of truth

Generated by walking `site/elfs/*.elf`, range-requesting each manifest, and
emitting:

```json
{
  "generated_at": "2026-05-07T12:34:56Z",
  "elf_count": 47,
  "elfs": [
    {
      "file_id": "intro_to_thermo",
      "title": "Introduction to Thermodynamics",
      "url": "/elfs/intro_to_thermo.elf",
      "size_bytes": 423817216,
      "has_model": true,
      "tags": ["physics", "thermodynamics", "intro"],
      "article_count": 8,
      "chunk_count": 47,
      "schema_version": "1.0",
      "elf_version": "1.0",
      "discriminator_score": 0.91,
      "created": "2026-05-07T12:34:56Z",
      "preview": {
        "first_paragraph": "Energy in a closed system is conserved...",
        "article_titles": ["The First Law", "Heat Engines", ...]
      }
    },
    ...
  ]
}
```

Build script: `tools/build_catalog.py` — walks `site/elfs/`, opens each ZIP,
reads `manifest.json` + the first chunk for the preview, writes
`catalog.json`. Idempotent.

## 4. Catalog page (`site/catalog/index.html`)

Same aesthetic as the landing page — black/orange/teal, IBM Plex Mono.

### Layout

- Nav (same as landing) — extra link "Catalog" highlighted as current
- Top bar: search input + tag filter chips + sort dropdown (newest /
  highest score / smallest)
- Grid of ELF cards (responsive, ~3 columns desktop, 1 column mobile)

### Card

```
┌──────────────────────────────────────┐
│ [physics] [thermodynamics]           │
│                                      │
│ Introduction to Thermodynamics       │
│ 8 articles · 47 chunks · 404 MB      │
│                                      │
│ "Energy in a closed system is..."    │
│                                      │
│ [ View ↗ ]  [ Download ↓ ]           │
│                                      │
│ score 0.91                created 5/7 │
└──────────────────────────────────────┘
```

- Tags: clickable, filter the grid
- "View" → opens `/view/?id=intro_to_thermo` (in-browser viewer, model
  loaded lazily from CDN)
- "Download" → direct `.elf` link, browser saves as file
- Score: dim if < 0.7, accent if ≥ 0.85
- Size badge color: green < 50MB (lite), orange 50–200MB, teal > 200MB
  (full model bundled)

### Search behavior

- Client-side, runs against `catalog.json` in memory
- Fields: title, tags, article titles, preview text
- No fancy ranking — substring match, case-insensitive, ranked by:
  score × tag-match-count
- Empty query shows everything sorted newest first
- Debounce 150ms on input

For v0, no full-text search across KB chunks. That requires either
range-requesting `kb.json` from every ELF (slow) or pre-extracting all
chunks into a separate index — defer to v0.2.

## 5. Viewer page (`site/view/index.html?id=...`)

This is the one users land on when they click "View" on a catalog card.
It's not "the ELF in an iframe" — it's a *re-rendering* of the ELF's KB
inside the site chrome, with an option to launch the full embedded runtime.

### Why not just iframe the ELF

Two reasons:
1. Iframing a 400MB ZIP forces the model download up front; users may just
   want to read the KB
2. The in-ELF runtime is optimized for offline single-file use; the catalog
   viewer should integrate with site nav, search, deep-links to articles

### Behavior

On load, given `?id=intro_to_thermo`:
1. Look up the entry in `catalog.json`
2. Range-request `manifest.json` + `kb.json` from the `.elf` (~tens of KB)
3. Render the KB in a Wikipedia-style two-pane layout (TOC left, content
   right) — same aesthetic as the existing `quarter_car.elf.html` demo
4. Show a top-of-page banner: "Want the offline assistant? [Launch model
   (404 MB)] or [Download .elf]"
5. If the user clicks Launch:
   - Stream the `model.gguf` entry from the ELF (or CDN fallback)
   - Load wllama with progress bar
   - Replace banner with chat input — same UI as inside an ELF runtime

### Deep links

`/view/?id=intro_to_thermo#article=first_law` should scroll to that article.
`?id=...&q=what+is+entropy` should open the chat with that prompt
pre-filled (after model load).

## 6. Generator UX (depends on Q4c — defer if Q4=b only)

Skipping for v0. Server-side generation with the discriminator costs money;
keep the website static until paid tier launches. Free users run
`elf_gen.py` locally + (eventually) `synthetic/generator.py` against their
own API key. The site only *hosts* generated ELFs — it doesn't generate them.

When this lands, a single page at `/create/` with:
- topic input + audience + accent color picker
- live progress (gen → discriminate → score → final ELF)
- "Add to public catalog" checkbox (default off; opt-in publishing)
- background: edge function calls a serverless worker that runs the pipeline

## 7. Free vs Paid gating

- **Free** (no auth): browse catalog, view any ELF, download any ELF, run
  `elf_gen.py` locally with own API key
- **Paid** (auth required): server-side generation, batch generation,
  discriminator scoring without paying for an API key, publishing to the
  public catalog without a CLI
- Auth: defer specifics. For v0, Stripe Checkout → email magic link →
  signed JWT in cookie. No user accounts table; the JWT carries entitlement
  expiry. Move to a real auth provider only if support burden warrants it.

The waitlist form on the landing page is the entry point until paid is
ready. `api/waitlist.js` is an edge function that pipes emails to wherever
(Resend, Buttondown, a Google Sheet via webhook — pick one when implementing).

## 8. The Qwen3 + wllama integration (depends on Q1 = both)

Same model serves two roles:

### Role A — assistant inside an ELF (per-ELF, offline)

- Loaded from `model/qwen3-0.6b-q4_k_m.gguf` inside the ELF
- System prompt: "You are an assistant for the document titled `{title}`.
  Answer questions about the embedded knowledge base. Cite article IDs."
- Context: chunk retrieval over `kb.json` — top-k chunks injected into
  prompt before user question. (Retrieval method TBD: keyword for v0,
  embeddings later.)
- No internet, no API key, no telemetry.

### Role B — generator (in-browser, on the site)

- Loaded once from a CDN URL (e.g. `/runtime/qwen3-0.6b-q4_k_m.gguf`),
  cached in OPFS
- System prompt: "You are an ELF KB generator. Output only valid JSON
  conforming to schema v{N}. Topic: `{topic}`."
- Output streamed as it generates; `elf_gen.build_html` runs once the JSON
  is complete and valid

### Fine-tuning data shape

The training corpus is `(prompt, KB-JSON)` pairs derived from the
synthetic pipeline:

```jsonl
{"prompt":"Topic: Kalman filters\nAudience: students\nAccent: #ff6b3d\nArticles: 6","completion":"{\"manifest\":{...},\"articles\":[...],\"chunks\":[...]}"}
```

Discriminator-filtered (score ≥ 0.8). One model per `schema_version`. When
schema bumps to 1.1, you fine-tune a new model and ship a new GGUF; old
ELFs keep working with their bundled v1.0 model.

## 9. Phase plan

**Phase A — `.elf` ZIP format + loader (1–2 days)**
- Define `manifest.json` schema as a Pydantic model (`tools/elf_format.py`)
- Update `elf_gen.py` to emit `.elf` (ZIP) instead of `.elf.html`. Keep
  HTML as a fallback if `--legacy-html` flag passed.
- Write `loadElfHeader` and `loadFullElf` in `site/runtime/`
- Test on the existing `quarter_car` KB — produce both formats, verify
  round-trip

**Phase B — catalog page (2 days)**
- `tools/build_catalog.py` — walks `site/elfs/`, emits `catalog.json`
- `site/catalog/index.html` + `runtime/catalog.js` — static-rendered grid
- Search + tag filters (client-side, in-memory)
- Add a few seed ELFs (the `quarter_car` demo + 2–3 generated samples) so
  the catalog is non-empty on launch

**Phase C — viewer (2–3 days)**
- `site/view/index.html` + `runtime/viewer.js`
- Range-request manifest + KB without downloading model
- Wikipedia-style two-pane render
- Lazy model load when user clicks Launch
- Deep links (`#article=`, `?q=`)

**Phase D — Qwen3 wllama wiring (1–2 days)**
- Bundle wllama into `runtime/`
- Boot loader: detect model presence in ELF → wllama init
- Same loader code reused by viewer (Role B)
- Streaming output to chat UI

**Phase E — fine-tuning loop (open-ended)**
- Once `synthetic/` pipeline produces filtered data, set up a training
  job (modal.com or Lambda Labs, a few hundred dollars)
- Output: `qwen3-0.6b-elf-v1.0-q4_k_m.gguf`
- Drop into `runtime/` and `model/` paths; existing loaders pick it up
- Repeat per schema version

## 10. Open questions (resolve before Phase A)

1. `.elf` MIME type — register `application/vnd.elf+zip` or use
   `application/zip`?
2. Are ELFs with `has_model: false` allowed in the public catalog, or
   does the catalog require fully-offline-capable ELFs?
3. Discriminator score threshold for catalog inclusion — current draft
   says > 0.8 for training data; same threshold for public catalog, or
   stricter?
4. CDN: where do shared model weights live? GitHub Releases (free, slow,
   bandwidth-capped), Cloudflare R2 (cheap), HuggingFace (free, designed
   for this)?

My defaults if you don't answer: `application/zip` (simpler), allow lite
ELFs (better catalog UX), 0.8 threshold (consistent), HuggingFace (free
+ standard).
