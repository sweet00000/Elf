The format

What's in a .elf

An .elf is a single portable file (HTML in v0.2, ZIP in v1.0) bundling everything a reader needs to open, browse, and chat with a knowledge base — entirely offline.

[01]
Manifest
RFC 8785 JCS-canonical JSON. SHA-256 over the manifest = the artifact's identity. Lists every resource inside, signed or unsigned.
[02]
Corpus
Articles + chunks. Embeddings precomputed. Sources preserved with provenance so the assistant can cite line spans back to originals.
[03]
Runtime
A wllama (GGUF) or transformers.js (ONNX) bootstrap inlined into the file. Boots a chat UI when opened. No installation, no server.
[04]
Optional model
A small LLM (~200MB–1GB) baked in for full offline use, or fetched lazily from a CDN for slim "lite" artifacts. Same runtime either way.
Hard commitments

What we won't compromise on.

  • [01]   Browser-only at the consumer edge. Open an .elf in any modern browser. No installation, no server, no telemetry.
  • [02]   Offline-first. External calls gated by an explicit API key. Absence ⇒ local fallback. Never crash for missing keys.
  • [03]   Manifest is identity. SHA-256 of the canonicalized manifest is the artifact's fingerprint. Same fingerprint ⇒ same artifact, byte for byte.
  • [04]   Citations are structured. Every grounded answer carries machine-readable citation spans, not regex over freeform prose.
  • [05]   Foundry is Python only. No Node deps in the synth pipeline. Forge/NotebookELF/Webelves stay browser-native.
Forge — `.elf` Builder

Build .elf in the browser.

Forge is a browser-only Solid app where a user — or an agent the user is chatting with — assembles a portable .elf from sources, embeddings, runtime templates, and an interaction contract. Output is one self-contained HTML file that runs offline anywhere.

[01]
Three-column workspace
Sources / pipeline / outputs on the left. Toolbar + chat in the middle. Sandboxed iframe preview on the right — same code path consumers run.
[02]
Manifest is truth
manifest$ + resources$ + blobs are the source of truth. Everything else derives. Identity = JCS canonical SHA-256, live in the toolbar.
[03]
Two runtimes ship
runtime-transformers-onnx.js for Xenova ONNX models. runtime-wllama-gguf.js for GGUF via WASM. Static templates copied into every output.
The plan — Forge M0 → M2

Architectural commitments

  • Solid + Vite + Tailwind. No React. Solid signals = state primitive.
  • Browser-only. No server. OPFS = filesystem. Workers do heavy work.
  • Tools = typed functions; both UI and agent call the same surface.
  • Identity = RFC 8785 JCS canonical SHA-256 over manifest with signatures: [].
  • Preview = sandboxed iframe loading the actual built .elf blob.
  • One AgentClient interface, MVP impl GeminiAgentClient. Local-model impl later.

ELF v0.2 manifest

  • elf_version: "0.2", id, title, created
  • resources[] with {id, media_type, sha256, role, derived_from[]}
  • interaction: {kind, operations[]} + fulfillments: {op: [resource_id]}
  • signatures[] + provenance

NotebookELF — Multi-notebook shell

NotebookLM-style. Builds .elf.

A browser studio for producing .elf "embeddable teachers." Dashboard of notebook cards. Each notebook holds sources, an auto-generated identity, a grounded RAG chat with inline citations, and a studio for notes. Hit Build and the whole teacher packages into one portable file — same chat UX baked in.

[01]
Three-panel notebook
Sources (left) — what the teacher knows. Chat (center) — ask, teacher cites. Studio (right) — your notes, build-time only.
[02]
Citations are structured
Gemini responseSchema forces {output: [{text, citations: [...]}]}. No regex over freeform output. Same shape the .elf runtime emits.
[03]
Out-of-band presentation
Icon, color, example questions live in notebookMeta, not in the manifest. Changing the icon doesn't change the artifact fingerprint.
The plan — Phases 1–6

OPFS layout

  • /notebooks/index.json — dashboard summaries
  • /notebooks/<id>/workspace.json — per-notebook snapshot (workspace + meta + chats + notes)
  • /notebooks/<id>/blobs/<sha[0:2]>/<sha> — content-addressed
  • /notebooks/<id>/outputs/<buildId>.elf.html — built artifacts

Codelves — AgentOS IDE

Many agents, one workspace.

Codelves is a browser-native, local-first multi-agent workspace. TXT-first threads as durable human-readable truth. One kernel worker, one shared Pyodide worker, many agent workers. Real Python in a tab.

[01]
Mode 1 — Recursive spawning
One app instance, many agents. Many thread files. Many child agent windows. Multiplied resource = agents, not app instances. v2 core, shipped.
[02]
Mode 2 — Nested child shell
Generated child copy of Codelves launches in a preview pane. Separate identity + storage namespace. May be preview-only. v2.1 target.
[03]
Mode 3 — Isolated runtime
Nested child becomes a real runtime: own kernel, agent workers, Pyodide, threads, workspace. Bounded by outer-system policy.
[04]
Mode 4 — Bot factory
Outer app spawns specialized child runtime configured for a user task, optionally with a local model stack. Roadmap; shape in v2.1, impl later.
The plan — v2.1

Namespace model

  • Every app instance has a namespace id: main, child-001..N, bot-001..N
  • Every durable path / worker graph / runtime resource belongs to an instance namespace
  • Prevents IndexedDB + OPFS + worker collisions across nested instances

Shipped features

  • File explorer with drag-to-resize panel
  • Code editor + Browser Preview tabs
  • Real-time chat (file-based at .agency/orchestrator/chat.txt)
  • Pyodide Python runtime in-browser
  • Multi-agent instances (Elves + Bots)
  • OPFS persistent storage, snapshot/restore, export/import
  • LLM backends: Gemini, Ollama, LM Studio, local Transformers.js

Open work

  • Mode 2 nested shell impl
  • Mode 3 isolated runtime
  • Tighter .elf integration: bake completed Codelves session as a .elf archive (project state + replay UI)

Webelves — Local search

Perplexity, offline.

A static, browser-native Perplexity-style search engine. All inference runs client-side via wllama (llama.cpp compiled to WASM+SIMD). The AI is called QAi — it reads the web, grounds answers in real sources, cites them inline.

[01]
Single engine, many tabs
One wllama Worker runs in the page. Every tab shares it. A small runExclusive queue guarantees one completion at a time. Non-active tabs with pending work show a "waiting" badge.
[02]
Pluggable search
SearchAdapter is a 2-method interface (search, fetchPage). SearXNGAdapter ships. CORSProxyAdapter + ExtensionAdapter stubs planned for v1.5.
[03]
Grounded answers
Top 4 pages fetched → Readability-extracted → chunked → MiniLM-embedded → cosine-ranked → top 5 chunks feed a "cite as [N]" prompt. Citations become clickable chips that scroll the source card into view.
[04]
Memory, transparent
After each chat (not search), the model extracts 0–3 durable facts. Stored in OPFS memories.json. All memories visible / editable / wipeable in Settings → Memory.
The plan — v1 → v1.5

Stack

  • Vite + React 18 + TypeScript + Tailwind
  • Zustand (tabs, sessions, generation queue)
  • react-resizable-panels (QAi side panel)
  • @wllama/wllama (GGUF runtime, Web Worker, WASM v1)
  • @xenova/transformers (MiniLM-L6-v2 embeddings, separate worker)
  • @mozilla/readability (main-text extraction)

Model slots

  • Default — SmolLM2-360M-Instruct Q4_K_M (~230MB)
  • Quality — Gemma-3-1B-Instruct Q4_K_M (~800MB, split into ≤512MB chunks)

COOP/COEP

  • wllama multi-threading needs cross-origin-isolated context
  • public/_headers sets Cross-Origin-Opener-Policy: same-origin + Cross-Origin-Embedder-Policy: require-corp
  • Without those, wllama silently drops to single-thread

Not in v1

  • WebGPU / WebLLM path (wllama roadmap, stubbed)
  • Extensions / CORS-proxy adapters (interfaces in)
  • Fine-tuning / LoRAs — personalization is retrieval-only
  • Accounts, sync, mobile layout polish

Foundry — Python GAN · paid tier

Bootstrap the wiki brain.

A Python pipeline that synthesizes .elf artifacts at scale, scores each one with a discriminator, and accumulates the high-scoring subset as a fine-tuning corpus. Goal: a 1–3B model that emits valid .elf content offline, in-browser.

seeds.yaml → generator → candidate.elf → discriminator → verdict
↑ refinement loop ←──── critique ←────┘
accepted → wiki-brain.jsonl → fine-tune → in-browser .elf-emitter
# with key — full pipeline
foundry loop --seeds seeds/topics.yaml --workers 4
# offline — stub generator + heuristic discriminator
foundry loop --offline --seeds seeds/topics.yaml
The plan — Foundry phases

Hard constraints

  • Python only. No Node deps in the runtime.
  • Offline-first. Every external call gated by ELF_LLM_API_KEY. Absence = local fallback. Never crash.
  • Discriminator only judges what its phase produces — no scoring features for unbuilt content.
  • Key-input scaffolded today, dormant. Paid features wired behind the same slot when they ship.

Phases

PhaseGoalStatus
0Landing page (this site, product tabs, plan links)in progress
1Foundry scaffold — pyproject.toml + foundry/{config,cli}.pynot started
2Inspector + Python builder (re-impl of forge buildSingle)not started

Discriminator rubric

  • Functionality (Playwright runtime checks) — weight 0.5, hard fail if model never loads
  • Depth (corpus tokens × tool count, log-scaled) — weight 0.3, capped to avoid rewarding bloat
  • Size efficiency (depth_score / log(bytes)) — weight 0.2, penalizes > 50MB unless depth justifies
  • Composite — accept if ≥ 0.7 AND functionality ≥ 0.6. LLM judge can veto.
